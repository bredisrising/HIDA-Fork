1. The Big Picture: What is HIDA and Why Does It Exist?

Imagine you've trained a neural network (like ResNet or GPT) in PyTorch. Normally, you'd run it on a GPU. But what if you want to run it on a custom chip (FPGA) that can be far more power-efficient? The problem is: FPGAs don't understand Python or PyTorch. They need a hardware design specified at a very low level.

HIDA (Hierarchical Dataflow Architecture) is a compiler that bridges this gap. It takes your PyTorch model and automatically produces optimized C++ code that a downstream tool (AMD Vitis HLS) can turn into actual FPGA hardware.

PyTorch Model (Python) | v Torch-MLIR (translates to MLIR) | v +--------------------------+ | HIDA Compiler | | (this codebase) | | | | 14 optimization stages | | ~ 55 compiler passes | +--------------------------+ | v Optimized HLS C++ Code (with #pragma directives) | v AMD Vitis HLS (translates to hardware) | v FPGA Bitstream (.xclbin) (runs on physical chip)
Why this matters Without HIDA, a human engineer would need to manually write thousands of lines of pragma-annotated C++ code, manually decide how to tile loops, partition arrays, pipeline computations, and organize data flow. HIDA automates all of this, achieving up to 3825x speedup over unoptimized baseline designs.

2. Hardware Background: What is an FPGA?

A GPU is like a factory with thousands of identical workers on a fixed assembly line. An FPGA is like a pile of LEGO bricks — you design your own custom factory, with custom assembly lines, custom conveyor belts, and custom storage bins, all tailored to exactly the computation you need.

2.1 What's Inside an FPGA

LUTs (Look-Up Tables)

The basic building blocks. A LUT is a small truth table that can implement any simple logic function. Think of them as the "neurons" of the FPGA — individually simple, but powerful in combination. Modern FPGAs have millions of them.

DSPs (Digital Signal Processors)

Specialized multiply-accumulate units hardwired into the FPGA. A single DSP can do one multiplication per clock cycle. Neural network inference (which is mostly matrix multiplies) consumes lots of DSPs. The AMD Alveo U55C has ~9,024 DSPs.

BRAM (Block RAM)

Small, fast on-chip memory blocks (18 Kbit or 36 Kbit each). Data stored in BRAM can be accessed in 1-2 clock cycles. HIDA uses BRAM for intermediate computation buffers between dataflow tasks. Total: ~5 MB on a large FPGA.

URAM (Ultra RAM)

Larger on-chip memory blocks (288 Kbit each). Slightly slower than BRAM but much denser. Used when BRAM runs out. Total: ~30 MB on a large FPGA.

HBM / DDR (External Memory)

Off-chip memory (gigabytes). Much higher capacity but much higher latency (~100ns vs ~1ns for BRAM). The AMD Alveo U55C has 16 GB of HBM with 32 channels providing ~460 GB/s bandwidth. Weights and large activations live here.

Routing Fabric

Programmable wires connecting everything. The routing is what makes an FPGA "programmable" — after you design your circuit, the FPGA's wires are configured to connect your LUTs, DSPs, and BRAMs the way you need.

2.2 Key Concepts

Clock Frequency

FPGAs typically run at 100-300 MHz (compared to GPUs at 1-2 GHz). They compensate by doing many things simultaneously in parallel — custom data paths, many operations per cycle.

Parallelism on FPGAs

Unlike a CPU (which executes instructions one-by-one) or a GPU (which has fixed parallel cores), an FPGA lets you create exactly the parallelism your algorithm needs. For a matrix multiply, you could create 64 multipliers working simultaneously, connected by custom data paths.

3. HLS Background: What is High-Level Synthesis?

Traditionally, you design FPGA hardware using RTL (Register-Transfer Level) languages like Verilog or VHDL. This is extremely tedious — you're specifying individual wires, registers, and clock cycles.

High-Level Synthesis (HLS) lets you write in C++ instead. A tool like AMD Vitis HLS reads your C++ and automatically generates the RTL hardware design. But the catch is: the C++ must be annotated with special #pragma directives that tell the HLS tool how to build the hardware.

3.1 The Pragmas That Matter

#pragma HLS PIPELINE II=N

Tells the tool to pipeline a loop — overlap successive iterations so a new iteration starts every N clock cycles. II=1 is the best: one new input per cycle.

// Without pipelining: each iteration takes 5 cycles, total = 5 * 100 = 500 cycles
// With PIPELINE II=1: first result at cycle 5, then one per cycle. Total ≈ 104 cycles
for (int i = 0; i < 100; i++) {
  #pragma HLS PIPELINE II=1
  output[i] = a[i] * b[i] + c[i];
}
Pipelining is like a car wash. Without it, you wash one car completely before starting the next. With pipelining, car 2 enters the soap stage while car 1 is in the rinse stage — multiple cars are being processed simultaneously at different stages.

#pragma HLS DATAFLOW

Tells the tool to run sub-functions in parallel like an assembly line. Instead of finishing function A, then starting function B, both run at the same time — A produces data that B consumes as it becomes available.

void top(float* in, float* out) {
  #pragma HLS DATAFLOW
  float mid1[64], mid2[64];
  stage_A(in, mid1);    // These three run
  stage_B(mid1, mid2);  // in parallel like
  stage_C(mid2, out);   // an assembly line
}
Dataflow is like a factory assembly line. Station A bends metal, station B paints it, station C packages it. All three stations work simultaneously on different items. The "items" flowing between stations are stored in small buffers (the mid1, mid2 arrays).

#pragma HLS ARRAY_PARTITION

Splits an array across multiple physical BRAM banks so multiple elements can be read/written simultaneously. Without this, BRAM can only serve 1-2 accesses per cycle (it's like a library with only 2 checkout counters).

float buf[64];
#pragma HLS ARRAY_PARTITION variable=buf cyclic factor=8 dim=1
// Now buf is split into 8 banks: buf[0],buf[8],buf[16],... in bank 0
//                                buf[1],buf[9],buf[17],... in bank 1
// etc. Up to 8 parallel accesses per cycle.

#pragma HLS STREAM

Declares a variable as a FIFO (First-In-First-Out) queue instead of regular memory. Used for dataflow communication.

hls::stream<float> fifo;
#pragma HLS STREAM variable=fifo depth=4
// fifo can hold 4 elements. Writer blocks if full, reader blocks if empty.

#pragma HLS INTERFACE

Specifies how the kernel connects to the outside world (DDR/HBM memory, control bus).

void kernel(float* weights, int n) {
  #pragma HLS INTERFACE m_axi port=weights  // AXI master (reads from DDR)
  #pragma HLS INTERFACE s_axilite port=n     // AXI-Lite slave (control reg)
  #pragma HLS INTERFACE s_axilite port=return // for start/done signals
}
The Core Challenge HIDA Solves Getting these pragmas right is an art. The wrong tiling size, the wrong partition factor, the wrong pipeline target — any of these can make the design 10-100x slower than optimal, or fail to meet resource constraints entirely. HIDA's job is to automatically find good pragma configurations.

4. MLIR Background: The Compiler Infrastructure

HIDA is built on MLIR (Multi-Level Intermediate Representation), a compiler framework from the LLVM project. To understand HIDA, you need to understand a few MLIR concepts.

4.1 What is MLIR?

MLIR is a system for building compilers. It gives you tools to define your own intermediate representations (IRs) — the internal languages that a compiler works with between the input (e.g., PyTorch) and the output (e.g., C++ code).

If a compiler is a translation bureau, MLIR is the bureau's framework for creating specialized translators. Instead of translating French directly to Japanese (very hard), you go French → English → simplified English → Japanese. Each intermediate language is designed to make certain transformations easy.

4.2 The Core Concepts

Operations (Ops)

Everything in MLIR is an Operation. An op takes inputs, produces outputs, and may contain nested code. Think of it as a very flexible instruction.

// A simple add: takes %a and %b, produces %result
%result = arith.addi %a, %b : i32

// A loop: takes nothing, but contains a body (region)
affine.for %i = 0 to 64 step 1 {
  // body operations here
}

// A function: has a name attribute and a body region
func.func @forward(%input: tensor<64x64xf32>) -> tensor<1000xf32> {
  // body
}

Every op has four parts:

  • Operands — input values (%a, %b)
  • Results — output values (%result)
  • Attributes — compile-time constants (like the 64 in the loop bound)
  • Regions — nested code blocks (the { ... } body of a loop or function)

SSA (Static Single Assignment)

In MLIR, every value is defined exactly once. You never "reassign" a variable — you always create a new one. This makes it easy for the compiler to track where data flows.

// NOT allowed in SSA:
// %x = 5
// %x = %x + 1   (reassignment!)

// SSA version:
%x0 = arith.constant 5 : i32
%x1 = arith.addi %x0, %one : i32    // new value, new name

Types

Every value has a type. MLIR has built-in types and lets dialects define custom types.

i32                        // 32-bit integer
f32                        // 32-bit float
index                      // loop index type
tensor<64x64xf32>          // immutable 64x64 float tensor
memref<64x64xf32>          // mutable 64x64 float buffer (pointer-like)
hls.stream<f32, 4>         // HIDA's custom FIFO type (depth=4)

Dialects

A dialect is a collection of related ops, types, and attributes under a namespace. Different dialects represent different levels of abstraction:

DialectAbstraction LevelExample
torchPyTorch opstorch.aten.linear
tosaTensor operationstosa.conv2d, tosa.matmul
linalgLinear algebra on tensorslinalg.conv_2d_nchw_fchw
affineLoop nests with affine boundsaffine.for, affine.load
memrefMemory operationsmemref.alloc, memref.load
arithArithmeticarith.addi, arith.mulf
hlsHIDA's custom HLS opshls.dataflow.dispatch, hls.dataflow.node

Compilation works by progressively lowering from high-level to low-level dialects. torch → tosa → linalg → affine + hls → C++ output.

Passes

A pass is a transformation that reads the IR, analyzes it, and rewrites it. For example, a "loop tiling" pass takes large loops and breaks them into smaller tiled loops. HIDA has ~55 passes organized into a pipeline.

Tensor vs. Memref

This distinction is critical and trips up many newcomers:

tensor (value semantics)

tensor<64x64xf32> is an immutable mathematical object — like a matrix in math class. When you "modify" a tensor, you actually create a brand new tensor. Tensors have no physical address in memory.

Used in: Early pipeline stages (linalg ops, fusion analysis). Easier to reason about because there are no side effects.

memref (pointer semantics)

memref<64x64xf32> is a typed pointer to a memory buffer. You can read and write to specific addresses. A memref maps to a real array in the generated C++ code.

Used in: Later pipeline stages (affine loops, hardware generation). Required because actual hardware has physical memory.

HIDA's pipeline starts with tensors and converts to memrefs in stage 3 (the "bufferization" pass). After that point, everything is memref-based.

7. The Two-Level Dataflow IR

This is HIDA's central design idea and the key to understanding the whole system.

7.1 Why Two Levels?

Building a hardware dataflow pipeline requires answering two very different kinds of questions:

  1. What should run in parallel? (algorithm-level question) — which computations can overlap?
  2. How should the hardware be wired? (microarchitecture-level question) — what buffers, what sizes, what connections?

Answering both at the same time is too complex. So HIDA uses two IRs:

Functional Dataflow (High Level)

Answers: "What should run in parallel?"

  • DispatchOp — a block of work to parallelize
  • TaskOp — a unit of computation
  • Tasks have transparent regions — they can see variables from outside
  • Tasks are easy to fuse (merge two tasks into one) or split (break one task into two)

At this level, HIDA figures out the grouping of computations.

Structural Dataflow (Low Level)

Answers: "How should the hardware be wired?"

  • ScheduleOp — contains a scheduled graph of nodes
  • NodeOp — has explicit input/output ports
  • BufferOp — on-chip BRAM between nodes
  • StreamOp — FIFO channel for scalars
  • Nodes have isolated regions — they are self-contained

At this level, HIDA assigns physical resources (buffers, streams, memory types).

The LowerDataflow pass converts from functional to structural:

// BEFORE (Functional): Tasks share variables implicitly
hls.dataflow.dispatch {
  %buf = hls.dataflow.buffer : memref<16x16xf32>
  hls.dataflow.task {
    // can see %buf because regions are transparent
    affine.store %val, %buf[%i, %j] : memref<16x16xf32>
  }
  hls.dataflow.task {
    %v = affine.load %buf[%i, %j] : memref<16x16xf32>
  }
}

// AFTER (Structural): Nodes have explicit I/O ports
hls.dataflow.schedule {
  %buf = hls.dataflow.buffer : memref<16x16xf32>
  hls.dataflow.node(%buf) -> (%buf) {
  // ^--- inputs       ^--- outputs  (explicit ports)
    ^bb0(%out: memref<16x16xf32>):
      affine.store %val, %out[%i, %j]
  }
  hls.dataflow.node(%buf) -> () {
    ^bb0(%in: memref<16x16xf32>):
      %v = affine.load %in[%i, %j]
  }
}

7.2 The Legality Problem

A structural dataflow schedule must satisfy two rules before it can become valid hardware:

  1. Single Producer — each buffer must be written by exactly one node
  2. Single Consumer — each buffer must be read by exactly one node (or use fork nodes)

HIDA has dedicated passes to fix violations: EliminateMultiProducer and EliminateMultiConsumer. Once all violations are fixed, the schedule is marked legal.

8. The Full Compilation Pipeline (14 Stages)

The main pipeline is registered as hida-pytorch-pipeline. Here's every stage, what it does, and why.

Reading Tip Each stage has a "debug point" number (1-13). You can stop the pipeline at any stage using -hida-pytorch-pipeline="debug-point=5" to see the IR after stage 5.

Stage 0: TOSA Optimization

Input: TOSA dialect ops from Torch-MLIR. Output: Optimized TOSA ops converted to Linalg.

Torch-MLIR translates PyTorch ops to TOSA (Tensor Operator Set Architecture) — a standardized set of tensor operations. HIDA first simplifies the TOSA graph (removing redundant transposes), then converts everything to the linalg dialect, which is better for analysis.

Key pass: TosaSimplifyGraph — removes redundant transpose/reshape ops that Torch-MLIR inserts.

Stage 1: Fake Quantization (Optional)

Input: Linalg ops with float types. Output: Linalg ops with integer types (e.g., i8).

Converts floating-point operations to fixed-point integer operations. This is critical for FPGA efficiency — an 8-bit multiply uses far fewer DSPs than a 32-bit float multiply. The "fake" part means it quantizes the IR but doesn't train with quantization-aware training.

Stage 2: Linalg Optimization & Task Extraction

Input: Linalg ops. Output: DispatchOp containing TaskOps.

This is where HIDA first identifies the dataflow structure. The key pass, CreateDataflowFromLinalg, does pattern matching:

  • Convolution and matrix multiply ops become root tasks
  • Elementwise ops (ReLU, add, etc.) are fused into neighboring tasks
  • Reshape/padding ops are fused into their consumers

After this stage, the IR has a DispatchOp containing a graph of TaskOps connected by tensor values.

Stage 3: Bufferization

Input: Tensor-based IR. Output: Memref-based IR.

Converts immutable tensors to mutable memory buffers. After this stage, there are no more tensor types — everything is memref. This is a one-way door: you can't go back to tensor semantics.

Key pass: BufferizeDataflow — handles HIDA-specific bufferization: converts task results to buffer allocations, creates BufferOp instances.

Stage 4: Linalg to Affine Conversion

Input: Linalg generic ops. Output: Affine loop nests.

Converts high-level linalg operations (like linalg.generic) into explicit loop nests using the affine dialect. A matrix multiply becomes a triple-nested loop.

// BEFORE: linalg.generic (implicit loops)
linalg.generic {
  indexing_maps = [...], iterator_types = ["parallel", "parallel", "reduction"]
} ins(%A, %B) outs(%C) { ... }

// AFTER: explicit affine loops
affine.for %i = 0 to 64 {
  affine.for %j = 0 to 64 {
    affine.for %k = 0 to 64 {
      %a = affine.load %A[%i, %k]
      %b = affine.load %B[%k, %j]
      %c = affine.load %C[%i, %j]
      %prod = arith.mulf %a, %b
      %sum = arith.addf %c, %prod
      affine.store %sum, %C[%i, %j]
    }
  }
}

Stage 5: Affine Loop Fusion

Input: Many separate loop nests. Output: Fewer, fused loop nests.

Merges producer-consumer loops into single loops when possible. This reduces memory traffic — instead of writing an intermediate array and reading it back, the fused loop passes data through registers.

Stage 6: Buffer Placement

Input: Buffers with no memory type. Output: Buffers classified as BRAM or DRAM.

Decides where each buffer lives in the memory hierarchy:

  • Small buffers (below externalBufferThreshold, default ~16KB) → BRAM (fast, on-chip)
  • Large buffers → DRAM (slow, off-chip, but large capacity)

DRAM buffers are "hoisted" outside of tasks so they can be shared globally.

Stage 7: Loop Tiling

Input: Large loops. Output: Tiled loops (two-level: outer tile loop + inner point loop).

Breaks large loops into small tiles to fit data into on-chip BRAM. For example, a 64x64 matrix multiply with tile size 8 becomes four nested loops: the outer two iterate over 8 tiles, the inner two iterate within each 8x8 tile.

// BEFORE: one level
affine.for %i = 0 to 64 { ... }

// AFTER: two levels (tile size = 8)
affine.for %i_tile = 0 to 64 step 8 {       // outer: 8 tiles
  affine.for %i_point = 0 to 8 {             // inner: 8 elements per tile
    // i = i_tile + i_point
  }
}
Loop tiling is like reading a textbook: instead of reading one word at a time from the whole book (cache misses!), you read one page completely (fits in cache), then move to the next page.

Stage 8: Local Buffer Allocation

Input: Code accessing large DRAM arrays directly. Output: Code that copies DRAM data into small on-chip BRAM buffers before computing.

Creates tile-sized local buffers (BRAM) and inserts copy operations to load data from DRAM into BRAM before computation. This is critical for performance — accessing BRAM is ~100x faster than accessing DRAM.

Stage 9: Affine Loop Dataflow

Input: Affine loop nests. Output: DispatchOp/TaskOp hierarchy created from loop structure.

This is the second dataflow extraction pass (the first was in Stage 2 at the linalg level). Now operating on affine loops, it wraps each tiled loop body in a TaskOp and the outer tile loop in a DispatchOp.

Also: StreamDataflowTask converts scalar task outputs (like reduction results) to stream channels for hardware communication.

Stage 10: Lower & Fix Dataflow

Input: Functional dataflow (Dispatch/Task). Output: Legal structural dataflow (Schedule/Node/Buffer).

This is the big transition — three critical passes run:

  1. LowerDataflow — converts DispatchOp→ScheduleOp, TaskOp→NodeOp. Classifies each node's arguments as inputs (read-only) or outputs (written).
  2. EliminateMultiProducer — if two nodes write to the same buffer, creates separate buffers and copy nodes.
  3. EliminateMultiConsumer — if two nodes read from the same buffer, inserts a fork node that copies the data to separate buffers.

After this: ScheduleDataflowNode assigns a level (topological order) to each node using ALAP (As Late As Possible) scheduling.

Stage 11: Parallelize Dataflow

Input: Scheduled dataflow. Output: Parallelized dataflow (loops unrolled for hardware replication).

This is where HIDA's "Hierarchical" part kicks in. ParallelizeDataflowNode decides how many copies of each node to create:

  • Complexity-aware: Complex nodes (many ops) get higher unroll factors
  • Correlation-aware: Nodes that share data are unrolled together to maintain alignment

For example, if the unroll factor is 4, a node processing a 64-element array becomes 4 copies each processing 16 elements in parallel.

Stage 12: Memory Optimization

Input: Parallelized dataflow. Output: Memory-optimized dataflow.

  • ReduceInitialInterval — rebalances reduction trees to lower pipeline II
  • BufferVectorize — converts scalar buffer accesses to vector accesses (load/store 4 elements at once instead of 1)
  • AffineStoreForward — eliminates redundant loads by forwarding stored values

Stage 13: Convert to Functions

Input: ScheduleOp/NodeOp hierarchy. Output: Plain functions with calls.

Each NodeOp becomes a C++ function. Each ScheduleOp becomes a function body with #pragma HLS DATAFLOW. Buffer arguments become function parameters.

Also: CreateTokenStream adds stream-based synchronization tokens for DRAM access ordering.

Stage 14: Directive Generation

Input: Functions with loops. Output: Functions annotated with HLS pragmas.

  • LoopPipelining — marks innermost loops with #pragma HLS PIPELINE II=1
  • ArrayPartition — searches for optimal partition factors and applies them
  • CreateAxiInterface — wraps the top function with AXI bus interfaces
  • CreateHLSPrimitive — maps 8-bit multiplies to DSP-optimized primitives

9. Key Passes Explained in Detail

9.1 CreateDataflowFromLinalg

File: lib/Transforms/Dataflow/CreateDataflowFromLinalg.cpp

This pass identifies which operations form the "spine" of the dataflow graph. It uses pattern matching:

  1. Root ops: Convolutions (linalg.conv_2d_nchw_fchw) and matrix multiplies (linalg.generic with contraction indexing) become task roots.
  2. Forward fusion: Ops that consume a root's output (like tensor.pad, tensor.empty) are pulled into the root's task.
  3. Backward fusion: Ops that produce a root's input (like elementwise activation functions) are pulled into the root's task.

The result: a clean graph where each task is a "layer" of the neural network (conv + ReLU, matmul + bias, etc.).

9.2 ParallelizeDataflowNode (Intensity-Aware)

File: lib/Transforms/Dataflow/ParallelizeDataflowNode.cpp

Given a total unroll budget (e.g., 4), this pass distributes it across nodes proportionally to their computational complexity:

// Node A: complexity = 1000 ops, Node B: complexity = 200 ops
// Total schedule complexity = 1000
// Unroll factor = 4

nodeA_factor = 1 + 4 * 1000 / 1000 = 5   // gets more parallelism
nodeB_factor = 1 + 4 * 200  / 1000 = 1   // stays sequential

Then, if correlation-aware mode is enabled, nodes that share the same buffer have their unroll factors synchronized to avoid misaligned access patterns.

9.3 LowerDataflow

File: lib/Transforms/Dataflow/LowerDataflow.cpp

Converts the functional IR to the structural IR in two steps:

  1. LowerDispatchToSchedule: For each DispatchOp, find all "live-in" values (values defined outside but used inside). These become the schedule's explicit operands.
  2. LowerTaskToNode: For each TaskOp, classify its live-in values by analyzing memory effects:
    • If only read → input
    • If written → output
    • If not a memref/stream → param (scalar)

9.4 ComplexityAnalysis and CorrelationAnalysis

File: lib/Dialect/HLS/Analysis.cpp

ComplexityAnalysis counts the total "work" in each node by recursively walking the IR:

  • Each primitive op (add, multiply, load, store) counts as 1
  • A loop multiplies the body count by the trip count
  • An if-else takes the maximum of both branches

CorrelationAnalysis finds which nodes share data and how their loop indices relate. If node A writes buf[i*8+j] and node B reads buf[k*4+l], the analysis computes the mapping between (i,j) and (k,l), including scale factors. This lets the parallelization pass unroll both nodes in a coordinated way.

10. Code Generation: From MLIR to C++

File: lib/Translation/EmitHLSCpp.cpp (~2072 lines)

After all 14 stages, the IR is a tree of func.func operations containing affine loops, memref loads/stores, and arithmetic. The emitter walks this IR and prints C++ text.

10.1 How It Works

The emitter uses the Visitor pattern: it has a dispatchVisitor function that looks at each operation's type and calls the appropriate emitXxx() method. For example:

  • affine.for → emitAffineFor() → prints for (int v0 = ...) {
  • affine.load → emitAffineLoad() → prints float v1 = array[i][j];
  • arith.mulf → emitBinary() → prints float v2 = v0 * v1;
  • hls.dataflow.stream → emitStreamChannel() → prints hls::stream<float> s;

10.2 Type Mapping

10.3 Pragma Emission

The emitter reads the directive attributes attached to ops and emits corresponding pragmas:

  • LoopDirectiveAttr{pipeline=true, targetII=1} → #pragma HLS pipeline II=1
  • FuncDirectiveAttr{dataflow=true} → #pragma HLS dataflow
  • PartitionLayoutAttr{[cyclic], [4]} → #pragma HLS array_partition variable=x cyclic factor=4 dim=1
  • MemoryKindAttr{bram_t2p} → #pragma HLS bind_storage variable=x type=ram_t2p impl=bram

11. End-to-End Example: ResNet18

Let's trace how HIDA compiles a real model.

Step 1: PyTorch → MLIR

The user writes a Python script (samples/pytorch/resnet18/resnet18.py) that uses Torch-MLIR to export the model:

import torch
import torch_mlir

model = torchvision.models.resnet18(pretrained=True)
module = torch_mlir.compile(model, torch.randn(1,3,224,224),
                            output_type="TOSA")
print(module)  # outputs .mlir text

Step 2: HIDA Optimization

scalehls-opt resnet18.mlir \
  -hida-pytorch-pipeline="top-func=forward loop-tile-size=8 loop-unroll-factor=4"

This runs all 14 stages: TOSA simplification → Linalg fusion → Bufferization → Affine conversion → Loop fusion → Buffer placement → Tiling (8x8) → Local buffers → Dataflow extraction → Lowering → Multi-consumer/producer fixing → Parallelization (factor 4) → Memory optimization → Function conversion → Directive generation.

Step 3: C++ Emission

| scalehls-translate -scalehls-emit-hlscpp -emit-vitis-directives > resnet18.cpp

Step 4: What the Output Looks Like

The generated C++ has this structure (taken from the actual resnet18.cpp output):

// Auto-generated by HIDA
#include <hls_stream.h>
#include <ap_int.h>

// Node functions (one per dataflow stage)
void forward_node2(
  float v22[512][1000],  // DRAM weights
  float v23[8][8],       // Local BRAM tile
  int v24, int v25       // Tile indices
) {
  #pragma HLS inline
  for (int v26 = 0; v26 < 8; v26++) {
    for (int v27 = 0; v27 < 8; v27 += 2) {  // unrolled by 2
      #pragma HLS pipeline II=1
      float v28 = v22[(v26+(v24*8))][(v27+(v25*8))]; // Load from DRAM
      v23[v26][v27] = v28;                             // Store to BRAM
      float v29 = v22[(v26+(v24*8))][((v27+(v25*8))+1)];
      v23[v26][(v27+1)] = v29;
    }
  }
}

// Top-level dataflow function
void forward_node0(
  float v30[512][1000],  // Weights (DRAM)
  float v31[1000],        // Bias (DRAM)
  float v32[512],         // Input features
  float v33[1000]         // Output
) {
  float v34[1000];         // Accumulator
  #pragma HLS array_partition variable=v34 cyclic factor=2 dim=1
  #pragma HLS bind_storage variable=v34 type=ram_2p impl=lutram

  for (int v35 = 0; v35 < 8000; v35++) {
    #pragma HLS dataflow        // node2 and node1 run in parallel!
    int v36 = (v35 % 125);
    int v37 = (v35 / 125);
    float v38[8][8];           // Tile buffer (BRAM)
    #pragma HLS array_partition variable=v38 cyclic factor=2 dim=2

    forward_node2(v30, v38, v37, v36);        // Load tile from DRAM
    forward_node1(v32, v38, v31, v34, v33, v37, v36); // Compute on tile
  }
}
What HIDA Automated Here
  • Tiled the matrix multiply into 8x8 tiles (from the loop-tile-size=8 option)
  • Created local BRAM buffers for tiles (v38[8][8])
  • Applied #pragma HLS dataflow to run tile loading and computation in parallel
  • Applied #pragma HLS pipeline II=1 to innermost loops
  • Applied array_partition cyclic factor=2 to enable dual-port access
  • Unrolled the inner loop by 2 (from loop-unroll-factor=4)
  • Chose ram_2p impl=lutram for small buffers
All of this was fully automatic from a PyTorch model export.
