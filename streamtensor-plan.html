Part 0: Core Concepts You Must Understand

Why this section exists
These are the foundational building blocks. Without internalizing them, the implementation steps in Part 3 will feel arbitrary. Read this before touching any code.

0.1 MLIR Fundamentals

MLIR (Multi-Level Intermediate Representation) is a compiler infrastructure framework from Google/LLVM that lets you define and compose multiple IRs in a single framework. Both HIDA and StreamTensor are MLIR-based compilers.

Operations (Op)

The fundamental unit of computation. Every instruction is an Op. An Op has:

  • Operands — input SSA values
  • Results — output SSA values
  • Attributes — compile-time constants (integers, strings, arrays, affine maps, types)
  • Regions — nested code (0 or more)
  • Successors — CFG successors (rarely used in dataflow IRs)
// Example: a simple add op
%result = arith.addi %a, %b : i32
// Operands: %a, %b   Results: %result   Attr: none

Values and SSA

MLIR uses Static Single Assignment form. Every value is defined exactly once and may be used many times. Values come from:

  • Op results — %x = some.op
  • Block arguments — function/loop arguments

SSA means you cannot "reassign" — you always create new values. This is what makes optimization analysis easy.

Regions, Blocks, and Terminators

A Region is a list of basic blocks. A Block is a list of ops ending with a terminator (like return, yield, br). Regions can be:

  • Isolated from above — cannot reference values from outer scopes (like a function body)
  • Transparent (not isolated) — can capture values from outer scope (like a loop body)

KernelOp will be IsolatedFromAbove. STTaskOp will be transparent.

Types

Every SSA value has a type. Built-in types include i32, f32, index. Dialects define custom types like:

  • memref<4x8xf32> — typed buffer with layout
  • tensor<4x8xf32> — immutable tensor value
  • hls.stream<f32, 4> — HIDA FIFO channel
  • hls.itensor<...> — StreamTensor's new type

Attributes

Attributes are compile-time data attached to ops. They are not SSA values. Examples:

  • depth = 4 : i64
  • affine_map<(d0,d1) -> (d0*16+d1)>
  • tile_sizes = [16, 16, 8]

Custom attributes (like KernelTimingAttr) are defined in TableGen and hold structured compile-time data.

Dialects

A dialect is a namespace grouping related ops, types, and attributes. Dialects can call into each other. The compiler pipeline lowers from high-level dialects to low-level dialects progressively:

torch → linalg → affine
  → memref → llvm

HIDA/StreamTensor add the hls dialect as an intermediate level between Linalg and LLVM.

0.2 TableGen — How Ops and Types Are Defined

TableGen is a domain-specific language that generates C++ boilerplate from declarative specifications. MLIR uses it for ops, types, attributes, interfaces, and passes.

Defining an Op

def MyOp : HLS_Op<"my_op",
    [Pure, SameOperandsAndResultType]> {
  let summary = "Does something";
  let arguments = (ins
    AnyType:$input,
    I64Attr:$factor
  );
  let results = (outs AnyType:$output);
  let assemblyFormat =
    "$input attr-dict `:` type($output)";
  let hasVerifier = 1;
  let hasFolder = 1;
}

Defining a Type

def StreamType : HLS_Type<"Stream"> {
  let mnemonic = "stream";
  let parameters = (ins
    "mlir::Type":$elementType,
    "unsigned":$depth
  );
  let assemblyFormat =
    "`<` $elementType `,` $depth `>`";
}

For ITensorType, because it has an AffineMap parameter, you must set hasCustomAssemblyFormat = 1 and implement parse/print manually in C++.

Traits

Traits are reusable op properties checked at verification time:

  • Pure — no side effects
  • IsolatedFromAbove — region can't capture outer values
  • SingleBlockImplicitTerminator<"YieldOp"> — region has exactly one block that ends with YieldOp
  • SameOperandsAndResultType — all types match
  • NoMemoryEffect — doesn't read/write memory

Interfaces

Interfaces define methods that multiple ops can implement. Key MLIR interfaces:

  • MemoryEffectOpInterface — declares read/write/alloc effects
  • InferTypeOpInterface — op can infer its result types
  • RegionBranchOpInterface — describes region control flow (needed for SSA live-in/live-out analysis)

StageLikeInterface in HIDA is a custom interface that TaskOp implements.

0.3 The Affine Dialect

The affine dialect represents loops and memory accesses with linear arithmetic constraints. This is critical because StreamTensor uses affine maps to describe iteration patterns in ITensorType.

AffineMap

An AffineMap maps a tuple of dimension/symbol values to a tuple of results using affine (linear + constant) expressions:

// (d0, d1)[s0] -> (d0 * s0 + d1, d0)
affine_map<(d0, d1)[s0] ->
  (d0 * s0 + d1, d0)>

In ITensorType, the iteration map maps iteration indices → data tensor dimensions. Example: a row-major tile iteration over a 64×64 matrix with 16×16 tiles uses affine_map<(d0,d1) -> (d0, d1)>.

AffineForOp

affine.for %i = 0 to 64 step 16 {
  affine.for %j = 0 to 64 step 16 {
    // body
  }
}

Key attributes: lower_bound, upper_bound, step — all affine expressions. Used to derive tripcount = (ub - lb) / step and stepSize = step for ITensorType inference.

AffineMaps in Memref

// Default row-major layout
memref<64x64xf32>
// Custom strided layout
memref<64x64xf32, strided<[64,1]>>

The pack transformation (tensor.pack) changes the affine map of the underlying memref to a tiled layout. Understanding this is essential for the PackKernelInterfacePass.

0.4 The Linalg Dialect

Linalg represents structured computations over tensors/memrefs. HIDA and StreamTensor both start from Linalg after torch-mlir lowers PyTorch operations.

linalg.generic

The most flexible Linalg op — a named loop nest with explicit indexing maps:

linalg.generic {
  indexing_maps = [
    affine_map<(m,n,k) -> (m,k)>,  // A
    affine_map<(m,n,k) -> (k,n)>,  // B
    affine_map<(m,n,k) -> (m,n)>   // C
  ],
  iterator_types = [
    "parallel", "parallel", "reduction"
  ]
} ins(%A, %B) outs(%C) {
  ^bb0(%a:f32, %b:f32, %c:f32):
    %r = arith.mulf %a, %b
    %s = arith.addf %r, %c
    linalg.yield %s
}

This represents matrix multiply. The indexing maps tell the compiler which operand dimension maps to which loop dimension.

Tiling (scf.for + extract_slice)

Linalg tiling decomposes a large computation into small tiles:

scf.for %i = 0 to 64 step 16 {
  scf.for %j = 0 to 64 step 16 {
    %tile_in = tensor.extract_slice
      %A[%i, 0][16, 64][1, 1]
    %tile_out = linalg.matmul
      ins(%tile_in, ...) outs(...)
    %result = tensor.insert_slice
      %tile_out into %C[%i, %j]...
  }
}

The ConvertLinalgToKernelPass analyzes this pattern to infer ITensorType parameters from the extract_slice/insert_slice offsets and the loop bounds.

tensor.pack / tensor.unpack

Changes the physical layout of a tensor for better cache/memory performance:

// 64x64 → 4x4x16x16 (tiled)
tensor.pack %src inner_dims_pos=[0,1]
  inner_tiles=[16,16] into %dest
  : tensor<64x64xf32>
    -> tensor<4x4x16x16xf32>

StreamTensor's PackKernelInterfacePass inserts these around kernel boundaries. For static weight tensors, packing is folded at compile time (zero runtime cost).

0.5 SCF (Structured Control Flow) Dialect

scf.for with iter_args

The iter_args pattern is the same as ITensorWriteOp's destination-carried semantics:

// Loop carries a tensor value through iterations
%result = scf.for %i = 0 to 4
    step 1 iter_args(%acc = %init)
    -> tensor<4x4xf32> {
  %updated = some_op %acc, %i
  scf.yield %updated
}

The ITensorWriteOp uses the same pattern: %next = itensor_write %value into %prev_itensor. Each write updates the "cursor" into the FIFO stream.

scf.if / scf.while

These appear in generated DMA and converter code. The ping-pong buffer switch (0→1→0→...) is implemented as:

%pingpong = arith.remui %iter, %c2
scf.if %pingpong {
  // write to buffer[0]
} else {
  // write to buffer[1]
}

0.6 Bufferization — Tensors vs Memrefs

Critical Concept
Understanding the tensor/memref boundary is essential for Phase 5 (Lowering and Bufferization). Get this wrong and the IR will be invalid.

Tensor (value semantics)

tensor<4x4xf32> is an immutable value — like a mathematical array. Operations on tensors produce new tensors (SSA). Tensors do not have addresses — you can't take a pointer to them.

The compiler works with tensors at high-level stages for ease of analysis and transformation.

Memref (pointer semantics)

memref<4x4xf32> is a typed pointer with shape and layout metadata. Operations on memrefs have explicit read/write semantics. Memrefs have addresses — they correspond to actual memory allocations.

HLS C++ uses memrefs (mapped to arrays/pointers).

One-Shot Bufferization

MLIR's bufferization framework converts tensor ops to memref ops. It analyzes aliasing to determine when tensors can be updated in-place vs when a copy is needed.

HIDA calls mlir::bufferization::runOneShotBufferize(). StreamTensor's BufferizeDataflowPass extends this for KernelOp and StreamBufferOp.

Key rule: After bufferization, no tensor ops should remain (except at boundaries explicitly handled).

ITensor's Role

ITensor sits between tensor and stream. It has value semantics (SSA-based destination passing) but represents a streaming FIFO (side-effecting communication).

The destination-carried pattern makes ITensor look functional even though it's actually a side-effecting FIFO push/pop. This is resolved during LowerITensorToStreamPass: destination-carried ops become imperative stream read/write calls.

0.7 HLS (High-Level Synthesis) Concepts

These are the hardware concepts that the compiler is targeting. You must understand what the generated pragmas mean.

Pipeline and II (Initiation Interval)

Pipelining means overlapping execution of successive loop iterations. #pragma HLS PIPELINE II=1 tells Vitis HLS to schedule successive iterations to start 1 clock cycle apart.

II=1 is the best case: one new input consumed per cycle. II=2 means throughput is halved. The LP FIFO sizing algorithm uses II values to compute token accumulation between kernels.

for (int i = 0; i < N; i++) {
  #pragma HLS PIPELINE II=1
  output[i] = compute(input[i]);
}

Dataflow

#pragma HLS DATAFLOW enables task-level parallelism within a function. All sub-functions execute concurrently, communicating through HLS streams or ping-pong buffers.

void top(...) {
  #pragma HLS DATAFLOW
  task_A(in, middle1);
  task_B(middle1, middle2);
  task_C(middle2, out);
}
// A, B, C run in parallel pipeline

This is what KernelOp maps to — the kernel becomes a top function with DATAFLOW pragma, and each STTaskOp becomes a sub-function call.

HLS FIFO (hls::stream)

Vitis HLS's hls::stream<T> is a FIFO channel between tasks. Properties:

  • Blocking read — reader stalls if FIFO empty
  • Blocking write — writer stalls if FIFO full
  • Depth — number of elements the FIFO can hold
#pragma HLS STREAM variable=s depth=4
hls::stream<float> s;

Too small a depth → deadlock. Too large → wastes BRAM/URAM. LP FIFO sizing finds the minimum safe depth.

Initial Delay (D) and Pipeline II

For a pipelined HLS function:

  • Initial Delay (D) — clock cycles before the first output is produced
  • Pipeline II — steady-state cycles between successive outputs
  • Total Latency — D + (N-1)*II for N iterations

StreamTensor models token flow between kernels using these three numbers (extracted from Vitis HLS synthesis reports).

AXI Interface

AXI (Advanced eXtensible Interface) is the standard bus protocol for FPGA memory access:

  • m_axi — master AXI port, used by DMAs to read/write DDR/HBM memory
  • s_axilite — slave AXI-Lite port for control/configuration (scalar arguments)
  • axis — AXI-Stream port for streaming data between components
#pragma HLS INTERFACE m_axi port=weights
#pragma HLS INTERFACE s_axilite port=return

Ping-Pong Buffering

A technique to hide memory latency: while one buffer is being filled from DDR, the kernel reads from the other buffer. When the fill completes, they swap.

StreamTensor's StreamBufferOp (and ITensorConverterOp) implement this with depth=2 allocation. The DMA task and compute task are in a double-buffered producer-consumer relationship.

0.8 FPGA Architecture Concepts

BRAM and URAM

On-chip memories on Xilinx FPGAs:

  • BRAM — 18Kb or 36Kb blocks, dual-port, 1-2 cycle read latency
  • URAM — 288Kb blocks, single-port, higher density

FIFOs with small depths use registers (FF). Larger FIFOs use BRAM/URAM. The LP solver tries to minimize total BRAM/URAM used by FIFOs while preventing deadlock.

HBM (High Bandwidth Memory)

AMD Alveo U55C has 16GB HBM with 32 pseudo-channels, each providing ~14 GB/s bandwidth. Total ~460 GB/s.

StreamTensor's DMA generation creates one m_axi port per HBM channel. The GenerateConnectivityPass assigns which tensor goes to which HBM channel.

SLR (Super Logic Region)

Alveo U55C has 2 SLRs connected by SLR crossing wires. Cross-SLR communication has extra latency (1-2 cycles). The ILP graph partitioner assigns tasks to SLRs to minimize cross-SLR communication while balancing resource usage.

DSP48/DSP58

Dedicated multiply-accumulate units on FPGAs. A single DSP58 can do one 27×18 multiply per cycle. Matrix multiply kernels consume many DSPs; the resource allocation space in DSE tracks DSP budget.

0.9 Linear Programming (LP) and ILP

StreamTensor uses LP for FIFO sizing and ILP for graph partitioning. You do not need to be an LP expert, but you need to understand the formulation.

LP Basics

A Linear Program has:

  • Variables — continuous real numbers (e.g., FIFO delay values)
  • Objective — linear function to minimize/maximize
  • Constraints — linear inequalities/equalities

LP can be solved in polynomial time. We use GLPK (GNU Linear Programming Kit) as the solver, called from C++ via glp_prob* prob = glp_create_prob().

FIFO Sizing as LP

Objective: minimize sum of FIFO depths (proxy for BRAM used).

Variables: delay[i][j] — the delay at edge (i→j) in the kernel graph.

Constraint: for every pair of kernels (u,v), the sum of delays on any path from u to v must be ≥ a threshold that prevents deadlock.

The FIFO depth is derived from the max tokens that can accumulate given the delay and the II ratio between producer and consumer.

ILP for Graph Partitioning

Integer Linear Program — same as LP but variables are constrained to integers (or binary 0/1). Used to assign tasks to SLRs.

  • Binary variable x[i][s] = 1 if task i is on SLR s
  • Minimize: cross-SLR communication + resource imbalance
  • Constraint: each task assigned to exactly one SLR

ILP is NP-hard in general but small instances (few dozen tasks) solve quickly with GLPK's branch-and-bound.

0.10 MLIR Pattern Rewriting

Most MLIR passes are implemented as collections of rewrite patterns applied to the IR.

RewritePattern

struct MyPattern
    : OpRewritePattern<linalg::GenericOp> {
  LogicalResult matchAndRewrite(
    linalg::GenericOp op,
    PatternRewriter &rewriter) const override {
    // Check preconditions
    if (!isMatmul(op)) return failure();
    // Do the rewrite
    rewriter.replaceOpWithNewOp<KernelOp>(
      op, ...);
    return success();
  }
};

PatternRewriter API

Key methods used in every pass:

  • rewriter.replaceOpWithNewOp<NewOp>(old, args...) — atomically replace
  • rewriter.eraseOp(op) — delete with no replacement
  • rewriter.create<NewOp>(loc, args...) — insert new op
  • rewriter.setInsertionPointAfter(op) — control where new ops go
  • rewriter.inlineRegionBefore(src, dst, point) — move regions
  • rewriter.mergeBlocks(from, into, args) — merge basic blocks

Greedy Pattern Application

Most passes use applyPatternsAndFoldGreedily(region, patterns) which repeatedly applies all matching patterns until no more apply (fixpoint). This handles cases where one rewrite enables another.

The kernel fusion pass (Algorithm 2) is not a pattern rewrite — it's a graph algorithm that runs once on the whole module. It uses the pass infrastructure directly, not the pattern rewriter.

0.11 Destination-Carried Semantics (Critical for ITensorWriteOp)

Key Design Pattern
This is the most unusual aspect of ITensorType. It makes FIFO writes look functional even though they're side-effecting. 
// The dest operand is a "token" representing the FIFO cursor position
// Each write advances the cursor and returns the next position
%s0 = itensor_empty : !hls.itensor<...>           // cursor at start
%s1 = itensor_write %tile0 into %s0               // push tile0, cursor = 1
%s2 = itensor_write %tile1 into %s1               // push tile1, cursor = 2

// This is EXACTLY like scf.for iter_args:
%final = scf.for %i = 0 to N step 1
    iter_args(%s_iter = %s0) -> !hls.itensor<...> {
  %tile = compute(...)
  %s_next = itensor_write %tile into %s_iter
  scf.yield %s_next
}
// After lowering, each write becomes stream.write(%tile, %fifo)

Why this design? SSA form requires each value to be defined once. By making the "FIFO state" an SSA value, the compiler can track data flow through the FIFO using standard MLIR dominance/use-def analysis, enabling fusion, verification, and optimization without special-casing FIFOs.

0.12 Optuna and Bayesian Optimization for DSE

What Optuna Does

Optuna is a Python library for hyperparameter optimization. It uses Bayesian methods (TPE — Tree-structured Parzen Estimators) to find good hyperparameters in fewer trials than grid search.

import optuna

def objective(trial):
    tile = trial.suggest_int("tile", 4, 64)
    unroll = trial.suggest_int("unroll", 1, 16)
    latency = compile_and_estimate(tile, unroll)
    return latency

study = optuna.create_study()
study.optimize(objective, n_trials=100)

DSE Integration

StreamTensor's DSE loop:

  1. Optuna proposes (tile_size, unroll_factor, Cmax)
  2. Python calls C++ pipeline with these params
  3. C++ runs passes up through LowerITensorToStream
  4. Vendor HLS profiles each kernel (with caching)
  5. LP solver computes FIFO sizes
  6. Objective = estimated latency + resource penalty
  7. Optuna updates its model and proposes next trial

The critical insight: don't run full synthesis in the loop — just analytical estimates augmented by cached profiling data.

0.13 XRT (Xilinx Runtime) for Host Code

XRT API Concepts

// Load the compiled kernel
xrt::device dev(0);
xrt::xclbin xclbin("kernel.xclbin");
dev.register_xclbin(xclbin);
xrt::kernel k(dev, xclbin.get_uuid(), "top");

// Buffer Object (BO) = DMA-able memory
xrt::bo bo_in(dev, N*sizeof(float),
              k.group_id(0));
float* data = bo_in.map<float*>();
// Fill data... then sync to device
bo_in.sync(XCL_BO_SYNC_BO_TO_DEVICE);

// Run kernel
auto run = k(bo_in, bo_out, N);
run.wait();

xclbin and v++ Linking

The build flow:

  1. Vitis HLS compiles C++ → .xo (kernel object)
  2. v++ --link links .xo + connectivity.cfg → .xclbin
  3. Host C++ loads .xclbin via XRT at runtime

The connectivity.cfg file (generated by GenerateConnectivityPass) maps kernel AXI ports to specific HBM channels. Getting this mapping right is critical for bandwidth.

0.14 StreamTensor-Specific Concepts

ITensorType Parameters

The full type encodes the streaming access pattern of a tensor:

// Reading 16x16 tiles from a 64x64 matrix
// row-major, 4 rows × 4 cols of tiles
!hls.itensor<
  element_shape=[16,16],    // tile size
  trip_counts=[4,4],        // 4×4 iteration
  step_sizes=[1,1],         // step=1 tile
  iter_map=affine_map<(d0,d1)->(d0,d1)>
>

Data shape = element_shape × trip_counts = 64×64. The iter_map says: iteration index (d0,d1) maps to data dimension (d0,d1) — i.e., row-first tile order.

Layout Compatibility

Two itensors are layout compatible (can connect with a plain FIFO) iff they have the same element shape, same iteration space, and the same iter_map. If any of these differ, an ITensorConverterOp must be inserted.

Example: producer emits itensor<[16,16],[4,4],[1,1],(d0,d1)->(d0,d1)> (row-major tiles) but consumer expects column-major tiles. The converter does a buffer-based layout transformation.

Algorithm 1: Converter Buffer Size

Given incompatible source and result itensor types, compute the minimum ping-pong buffer size for the converter:

  1. Find the longest shared prefix of the iteration space where element sizes and maps agree
  2. The buffer holds all data elements below the shared prefix
  3. This is the smallest buffer that allows the converter to fully transform one "slice" before passing it on

Returns: (bufShape, beforeLoop) — buffer shape and which loop level is shared.

Algorithm 2: Greedy Kernel Fusion

Fuses kernels to minimize off-chip communication, subject to on-chip memory budget Cmax:

  1. Process kernels in topological order
  2. For each kernel n, find the nearest predecessor that can be fused with n (cost ≤ Cmax)
  3. If found, merge n into that predecessor's fusion group
  4. Otherwise create a new fusion group for n

Each fusion group becomes one physical kernel function. Inter-group communication uses DMAs (off-chip). Intra-group communication uses FIFOs (on-chip).

Token Flow Model

The LP FIFO sizing models how tokens (tensor tiles) accumulate between two kernels with different IIs:

  • If producer II < consumer II: tokens accumulate (need larger FIFO)
  • If producer II > consumer II: tokens drain (small FIFO OK)
  • The delay variable controls how long the consumer waits before starting, which determines peak token count

The LP finds the minimum total delay (= minimum total FIFO depth) that prevents overflow/underflow on all paths simultaneously.

KV Cache and Autoregressive Decoding

For LLMs, the main challenge is the KV cache — previously computed keys and values that grow with each generated token. StreamTensor handles this by:

  • Treating the transformer block as the compilation unit (not the full model)
  • Exposing KV cache as an external tensor argument that the host manages
  • The block is "triggered multiple times" (paper Section 6.1) — once per generated token

Part 1: How HIDA Works

1.1 Overview

HIDA (Hierarchical Dataflow Architecture) is an MLIR-based HLS compiler that transforms PyTorch models or C++ code into optimized dataflow architectures on FPGAs. The codebase lives at /home/ankit/dev/insta_research/HIDA-Fork and is built on the MLIR compiler infrastructure.

1.2 HIDA's Two-Level IR

HIDA models dataflow at two abstraction levels within a single hls dialect (mlir::scalehls::hls):

LevelOpRole
Functional Dataflow
(high-level, algorithm-oriented)		DispatchOpContains a graph of tasks to be dispatched in dataflow
TaskOpTransparent region containing ops to execute; can be fused/split freely
YieldOpTerminator returning results from dispatch/task
Structural Dataflow
(low-level, microarchitecture-oriented)		ScheduleOpIsolated region with scheduled nodes (counterpart of DispatchOp)
NodeOpIsolated region with explicit I/O: inputs (read-only), outputs (written), params (scalars)

StreamOpFIFO channel with stream_read/stream_write ops

1.3 HIDA Compilation Pipeline

The hida-pytorch-pipeline (lib/Transforms/Passes.cpp:140) proceeds in 14 stages:

  1. TOSA/Linalg optimization — elementwise fusion, dataflow creation from linalg patterns
  2. Bufferization — tensor IR → memref IR
  3. Linalg to Affine — linalg generics → affine loop nests
  4. Affine loop fusion — fuse producer-consumer loops
  5. Buffer placement — classify buffers as BRAM/DRAM based on size threshold
  6. Loop tiling — tile loops with configurable tile size
  7. Local buffer allocation — create tile-sized local buffers
  8. Affine loop dataflowing — create DispatchOp/TaskOp hierarchy from affine loops
  9. Lower dataflow — Functional (Task/Dispatch) → Structural (Node/Schedule/Buffer)
  10. Eliminate multi-producer/consumer — fix shared buffer violations
  11. Parallelize dataflow nodes — intensity-aware + connection-aware loop unrolling
  12. Memory optimization — reduce II, vectorize buffers
  13. Convert dataflow to func — nodes become sub-functions
  14. Directive generation — emit HLS pragmas, create AXI interfaces

Part 2: How StreamTensor Improves on HIDA

2.1 Improvement 1: ITensor Type System

HIDA uses standard memref between nodes. StreamTensor introduces itensor that encodes the full streaming access pattern at the type level. This enables the compiler to verify stream layout compatibility at type-check time and automatically insert layout converters when needed.

2.2 Improvement 2: Stream-Based Kernel Fusion

HIDA fuses tasks at the Linalg level (pattern matching). StreamTensor fuses at the dataflow kernel level using the itensor type. Any two adjacent kernels can be fused — if their communication layouts differ, a converter is automatically inserted. Algorithm 1 sizes the converter buffer, Algorithm 2 finds the optimal fusion grouping.

2.3 Improvement 3: Automatic DMA Generation

In HIDA, external memory interfaces are handled manually. StreamTensor's KernelOp has tensor I/O at its boundary. Conversions from tensor to itensor at the kernel boundary automatically become DMAs with ping-pong buffering and pack/widen transformations.

2.4 Improvement 4: LP-Based FIFO Sizing

HIDA uses fixed-depth buffers. StreamTensor models token production/consumption as piecewise linear functions, then solves an LP to minimize total FIFO area while preventing deadlock.

2.5 Improvement 5: Hierarchical DSE

Three nested design spaces: Linalg Tiling Space → Kernel Fusion Space → Resource Allocation Space. Searched via Optuna.

2.6 Improvement 6: LLM Support

HIDA targets CNNs (ResNet, MobileNet). StreamTensor targets LLMs (GPT-2, Qwen, Llama, Gemma) — fusing entire transformer blocks with all intermediate results streaming on-chip.

Handles non-linalg tensor ops (pad, collapse_shape, expand_shape, chunk, concat) between kernels → simple pass-through kernels.

Step 3.3: PackKernelInterfacePass

lib/Transforms/Dataflow/PackKernelInterface.cpp NEW

  1. For each kernel, examine input/output tensor types
  2. Insert tensor.pack before kernel to convert default layout → tiled layout
  3. Insert tensor.unpack after kernel to convert back

  5. For dynamic tensors (activations): attempt to fold pack/unpack with neighboring kernels

lib/Transforms/Dataflow/WidenKernelInterface.cpp NEW

Widens tensor elements to vectors for maximum memory bandwidth. With 512-bit DDR/HBM and uint8 elements, groups 64 elements into vector<64xi8>. Updates ITensorType element shapes accordingly.

Step 3.5: MaterializeKernelPass

lib/Transforms/Dataflow/MaterializeKernel.cpp NEW

Materializes the implicit DMA at kernel boundaries:

  1. Input boundary: generate scf.for loop that loads from packed tensor → ping-pong buffer → pushes to FIFO via ITensorWriteOp
  2. Output boundary: generate loop that pulls from FIFO → ping-pong buffer → writes to external memory
  3. These DMA tasks are wrapped in STTaskOp within the kernel
  4. After materialization: DMA-in tasks → compute tasks → DMA-out tasks

Algorithm 1 — Converter Buffer Size (ITensorConverterUtils.cpp) 
// Input: src ITensorType, res ITensorType
// Output: bufShape, beforeLoop (shared loop index)
//
// 1. Initialize bufShape=[], beforeLoop=0
// 2. For each data dimension dim:
//    a. if src.elementSize(dim) != res.elementSize(dim): break
//    b. Get srcExpr = src.iterMap result expr for dim
//       Get resExpr = res.iterMap result expr for dim
//    c. If both are affine.dim expressions at same position:
//       - append src.elementSize(dim) to bufShape
//       - record as shared, increment beforeLoop
//    d. Else: break
// 3. Filter out shared loops whose parents are not shareable
// 4. Append remaining full data shape to bufShape
// 5. Return {bufShape, beforeLoop}
std::pair<SmallVector<int64_t>, int>
computeConverterBufferShape(ITensorType src, ITensorType res);
Algorithm 2 — Kernel Fusion Exploration (StrategyMergeTask.cpp) 
// Input: G (kernel graph), Cmax (max on-chip memory per fused kernel)
// Output: fusion groups, costs
//
// F=[{∅}], C=[0], M={} // M maps node→fusion group index
// for n in topological_sort(G):
//   gather fusion candidates from predecessors in G
//   for each predecessor p:
//     compute memory cost of fusing n with p's group
//   select nearest valid candidate f_idx with cost f_cost
//   if no candidate or f_cost + C[f_idx] > Cmax:
//     create new fusion group {n}
//   else:
//     add n to group f_idx, update cost C[f_idx] += f_cost
// write fusion_index attr back to each kernel
void runFusionExploration(
    ModuleOp module,
    int64_t Cmax,
    DominanceInfo &domInfo);

Lowering and Bufferization

Step 5.1: LowerITensorToStreamPass (Critical)

lib/Transforms/Dataflow/LowerITensorToStream.cpp NEW

Converts itensor-level IR to stream-level IR:

  1. ITensorInstanceOp → StreamOp with depth from itensor analysis
  2. ITensorWriteOp → loop nest (from itensor iteration space) containing StreamWriteOp
  3. ITensorReadOp → loop nest containing StreamReadOp
  4. ITensorConverterOp → two loop nests connected by ping-pong StreamBufferOp
  5. ITensorForkOp → read once, write to N streams
  6. Strip all ITensorType metadata (not needed at stream level)
Key Semantic Shift
STTaskOp at itensor level uses destination-carried (functional) semantics. After lowering to stream level, tasks use mutable stream semantics — the same %stream SSA value is read/written without SSA chaining. The destination-carried chain is eliminated by the lowering pass.

Step 6.2: LP FIFO Sizing

lib/Transforms/DSE/LPFIFOSizing.cpp NEW

Full LP Formulation

Step 1 — Token Behavior Model: For each kernel, extract (pipelineII, initialDelay, totalLatency) from KernelTimingAttr.

Step 2 — Max Token Calculation for edge (src→dst):

// If src produces faster than dst consumes:
max_tokens = min(T, T - floor((L - delay) / II_dst))
// If src produces slower than dst consumes:
max_tokens = min(T, ceil((delay - D) / II_src))

Step 3 — LP Variables: delay[i][j] for each edge (i,j) — the scheduling delay at that FIFO.

Objective: minimize sum(max_tokens[i][j]) ≈ minimize total FIFO depth.

Constraints: for all pairs (u,v) and all paths between them: sum(delay[i][j] on path) ≥ threshold(u,v) where threshold prevents deadlock.

Solver: GLPK via glp_create_prob() / glp_simplex(). Fallback: heuristic depths if GLPK not available.

Potential Obstacles and Mitigations

Obstacle 1: ITensorType Custom Assembly Format

Problem: AffineMap parameter in a type requires manual parse()/print() implementation — TableGen assemblyFormat cannot handle it.

Mitigation: Start with a simplified ITensorType using identity maps only. Add full affine map support in a second pass. Reference: mlir/lib/IR/BuiltinTypes.cpp MemRefType::parse().

Obstacle 2: Destination-Carried Semantics in Loops

Problem: ITensorWriteOp's SSA-based destination passing must interact correctly with scf.for iter_args, RegionBranchOpInterface, and MLIR's live-in/live-out analysis.

Mitigation: Implement RegionBranchOpInterface on STTaskOp. Study tensor.insert_slice and scf.for in upstream MLIR for the exact pattern.

Obstacle 3: Vendor Tool Latency in DSE Loop

Problem: Vitis HLS synthesis takes minutes per kernel. 100 DSE iterations × N kernels = unacceptable compile time.

Mitigation: (1) Cache profiling results keyed by kernel hash. (2) Run kernel syntheses in parallel with std::async. (3) Use analytical estimates for early DSE iterations; profile only the final candidate. (4) Support --profiling-results=file.json flag to preload cached results.

Obstacle 4: LLM Dynamic Shapes

Problem: LLMs have dynamic sequence lengths. Torch-MLIR may produce dynamic-shape IR that the static-analysis-based ITensorType inference cannot handle.

Mitigation: Use torch.jit.trace with fixed max_seq_len. Alternatively, use torch-mlir's shape inference to specialize shapes. Compile one transformer block (not the full model). Handle KV cache as an explicitly-sized external memref.

Obstacle 5: MLIR Version Compatibility

Problem: HIDA is pinned to a specific LLVM/MLIR commit. Upstream API changes (especially in Linalg and SCF) may conflict.

Mitigation: Pin to the known-good LLVM commit in HIDA's CMakeLists.txt. Wrap any volatile APIs in utility functions to localize migration effort.

Obstacle 6: GLPK Dependency

Problem: GLPK may not be available on all build machines.

Mitigation: Make LP sizing optional via CMake option(SCALEHLS_ENABLE_LP "Enable LP FIFO sizing" OFF). Implement a heuristic fallback: depth = max(2, total_tokens / num_kernels).
