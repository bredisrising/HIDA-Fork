StreamTensor Official Documentation

Complete reference extracted from hanchenye.com/streamtensor — 5 dialects, 45+ passes, full Python API. This is our ground truth for implementation.

Key Insight vs. Original Plan The docs reveal that StreamTensor is a new project with its own dialects, not just modifications to the HIDA hls dialect. It introduces 5 new/extended dialects: dataflow, hls (new, different from HIDA's), tensor_ext, arith_ext, and runtime. The ITensorType and all streaming ops live in the dataflow dialect.

Important Difference from HIDA HIDA has one hls dialect with everything. StreamTensor splits concerns across 5 dialects. When implementing, we add these as new namespaces alongside HIDA's existing hls dialect — or we can reuse the same hls namespace and extend it. The docs show the hls dialect in StreamTensor is almost entirely different from HIDA's (no DispatchOp/TaskOp/NodeOp — those are replaced).

2. dataflow Dialect

2.1 Types

!dataflow.itensor<elementType, iterTripCounts, iterSteps, iterMap>

An iterative tensor — the core type of StreamTensor.

ParameterC++ TypeDescription
elementTypemlir::TypeThe element type of each tile (e.g., f32, i8, vector<4xf32>)
iterTripCountsArrayRef<int64_t>Number of iterations per dimension of the iteration space
iterStepsArrayRef<int64_t>Step sizes for each iteration dimension
iterMapmlir::AffineMapMaps iteration indices → tensor data dimensions

Example: A 64x128xf32 tensor tiled into 16x16 tiles (4 tiles in dim0, 8 tiles in dim1):

!dataflow.itensor<f32, iter_space: [4, 8] * [16, 16], iter_map: (d0, d1) -> (d0, d1)>

Note: iterTripCounts=[4,8], iterSteps=[16,16], iterMap=(d0,d1)->(d0,d1). The iterSteps encode the element shape (16x16 tiles). This type has custom assembly format because of the AffineMap parameter.

!dataflow.stream<elementType, memorySpace>

A FIFO channel between producer and consumer modules.

ParameterTypeDescription
elementTypemlir::TypeType of each FIFO element
memorySpacemlir::AttributeMemory implementation (BRAM, URAM, SRL, etc.) — optional

3. hls Dialect (StreamTensor's version)

Note StreamTensor's hls dialect is completely different from HIDA's hls dialect. It's focused on hardware connectivity, SLR assignment, and port mapping — not computation. The computation ops (Dispatch/Task/Node/Schedule) are gone.

9. Full Compilation Pipeline (from Python API)

The Compiler.hls_pipeline() method orchestrates these stages. This is the canonical compilation order:

# Pseudocode of the StreamTensor HLS pipeline

def hls_pipeline(module, config):

    # ── Stage 1: Linalg optimization ─────────────────────────────────
    apply_linalg_optimization_transforms(
        module,
        fake_quantize=config.fake_quantize,
        quantize_bitwidth=config.quantize_bitwidth,
        constant_quantize_bitwidth=config.constant_quantize_bitwidth,
    )
    # Passes: fuse-linalg-elementwise-ops, fuse-linalg-fill,
    #         linalg-fake-quantize (optional), generalize-named-ops

    # ── Stage 2: Intensity-aware tiling + convert to dataflow ────────
    apply_intensity_aware_linalg_tiling(
        module,
        entry_name="forward",
        default_tile_size=config.default_tile_size,
        overall_unroll_size=config.overall_unroll_size,
        max_vec_bitwidth=config.max_widen_bitwidth,
        convert_linalg_to_dataflow=True,
        max_trials=config.max_trials,     # 0 = deterministic
        op_ii_map=config.op_ii_map,
    )
    # Uses LinalgTilingDesignSpace to find tile/unroll/vec params
    # Then runs transform.dataflow.convert_tiled_linalg_to_kernel
    # Passes: raise-scf-to-affine, lower-pack-unpack, ...

    # ── Stage 3: Tensor → kernel ────────────────────────────────────
    apply_tensor_to_dataflow_conversion(module)
    # Passes: convert-tensor-to-kernel

    # ── Stage 4: Greedy kernel fusion ──────────────────────────────
    apply_greedy_kernel_fusion(
        module,
        entry_name="forward",
        max_fusion_cost=config.max_fusion_cost,  # 8000 BRAM/URAM words
    )
    # Uses KernelFusionDesignSpace.greedy_fuse_kernels()
    # Runs transform.dataflow.fuse_kernels

    # ── Stage 5: Dataflow optimization ─────────────────────────────
    apply_dataflow_optimization_transforms(
        module,
        buffer_kernel_interface=config.buffer_kernel_interface,
        max_widen_bitwidth=config.max_widen_bitwidth,
        constant_folding=config.constant_folding,
    )
    # Passes: pack-kernel-interface, widen-kernel-interface,
    #         materialize-kernel, fold-itensor, vectorize-itensor,
    #         ensure-itensor-single-use, convert-itensor-empty-to-instance
    #         simplify-task-structure, merge-data-driven-task (optional)

    # ── Stage 6: Bufferization ─────────────────────────────────────
    apply_bufferization(
        module,
        task_partition_merging=config.task_partition_merging,
        data_driven_task_merging=config.data_driven_task_merging,
        max_stream_depth=config.max_stream_depth,
    )
    # Passes: comprehensive-bufferize, lower-itensor-to-stream,
    #         reduce-stream-depth, merge-task-partition (optional),
    #         merge-data-driven-task (optional)

    # ── Stage 7: LP resource allocation ────────────────────────────
    if config.resource_allocation:
        # Profile tasks with Vitis HLS (parallel synthesis)
        apply_task_profiling(module, config=synthesis_config)

        apply_linear_programming_resource_allocation(
            module,
            entry_name="forward",
            pipeline_rewinding=config.pipeline_rewinding,
            stream_size_map=config.stream_size_map,
            strategy=config.stream_sizing_strategy,
            partition=config.partition,
            num_dsp=config.num_dsp,
            num_uram=config.num_uram,
            num_bram=config.num_bram,
            num_lut=config.num_lut,
            max_widen_bitwidth=config.max_widen_bitwidth,
            imbalance_threshold=config.imbalance_threshold,
        )
        # Uses StreamSizingDesignSpace + GraphPartitionDesignSpace
        # Pass: allocate-memory, reduce-stream-depth

    # ── Stage 8: HLS code generation ───────────────────────────────
    apply_hls_codegen(
        module,
        num_hbm_port=config.num_hbm_port,
        create_kernel_wrapper=config.create_kernel_wrapper,
        assign_slr=config.assign_slr,
    )
    # Passes: generate-directive, materialize-directive,
    #         convert-dataflow-to-func, generate-connectivity

    # ── Stage 9: Runtime (XRT) code generation ─────────────────────
    apply_runtime_codegen(
        module,
        host_func_name="host",
        timeout_in_ms=config.timeout_in_ms,
    )
    # Passes: generate-runtime-host-func, convert-memref-to-pointer

    return module

10. What This Changes in Our Implementation Plan

Major Revision Required The original plan was based on the paper alone. The docs reveal the actual implementation architecture, which differs in several important ways.

10.1 Namespace / Dialect Structure

AspectOriginal Plan (paper-based)Actual (docs-based)
ITensorType locationAdd to HIDA's hls dialectLives in a new dataflow dialect
StreamTypeKeep HIDA's hls.streamNew dataflow.stream with memorySpace attribute
KernelOp / TaskOpAdd to HIDA's hls dialectIn the new dataflow dialect
Connectivity/SLR opsN/A (not in paper)Separate hls dialect with 5 ops
QuantizationNot addressedSeparate arith_ext dialect
Tensor wideningPart of widening passSeparate tensor_ext dialect ops
XRT host codeGenerated C++ string outputSeparate runtime dialect, then lowered to C++

10.2 New Operations Discovered

  • dataflow.itensor_buffer — the "converter buffer" operation (Algorithm 1 in paper). Has bufferType, loopIndex, dimIndex attrs. This is distinct from ITensorConverterOp in our plan.
  • dataflow.itensor_reassociate — for reshape/expand/collapse of iteration space. Has expandShape, shapeReassociation, expandIteration, iterationReassociation attrs.
  • dataflow.buffer — on-chip buffer (memref), alongside stream ops
  • tensor_ext.widen / tensor_ext.unwiden — explicit widening ops on tensors
  • tensor_ext.chunk — tensor-level chunk (maps to dataflow.itensor_chunk)
  • All runtime.* ops — XRT abstraction layer

10.3 TaskOp is Different

The actual dataflow.task has dataDriven and kernel boolean flags — not the same structure as HIDA's TaskOp. The inits are optional (dest-carried), and the task is NOT always isolated from above.

10.4 Key Pipeline Differences

  • The conversion from linalg to dataflow happens via Transform Dialect sequences, not a monolithic pass. The transform.dataflow.convert_tiled_linalg_to_kernel op is the entry point.
  • Kernel fusion is driven by Python DSE code (KernelFusionDesignSpace.greedy_fuse_kernels()) which then writes a transform sequence back to the MLIR, run by -streamtensor-transform-interpreter.
  • LP FIFO sizing is in Python (StreamSizingDesignSpace), not a C++ pass.
  • Graph partitioning is in Python (GraphPartitionDesignSpace).
  • The overall orchestrator is the Python Compiler class.

10.5 Updated Implementation Priority

  1. Create dataflow dialect with ITensorType, StreamType, KernelOp, TaskOp, all ITensor/Stream ops (21 ops)
  2. Create tensor_ext dialect with 4 ops + VectorizationEncodingAttr
  3. Create arith_ext dialect with 4 quantization ops
  4. Create hls dialect (StreamTensor version) — can reuse HIDA's namespace with new ops added, or create parallel namespace
  5. Create runtime dialect with 18 ops + 2 types
  6. Implement all 45+ passes as listed above
  7. Implement Transform Ops: convert_tiled_linalg_to_kernel, fuse_kernels
  8. Implement Python DSE layer: LinalgTilingDesignSpace, KernelFusionDesignSpace, StreamSizingDesignSpace, GraphPartitionDesignSpace
  9. Implement Python compiler orchestration: Compiler class, transforms module, profiler, synthesizer
