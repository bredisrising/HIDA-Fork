# StreamTensor Implementation Plan: Building on HIDA

## Part 1: How HIDA Works

### Overview
HIDA (Hierarchical Dataflow Architecture) is an MLIR-based HLS compiler that transforms PyTorch models or C++ code into optimized dataflow architectures on FPGAs. It lives at `/home/ankit/dev/insta_research/HIDA-Fork` and is built on the MLIR compiler infrastructure.

### HIDA's Two-Level IR
HIDA models dataflow at two abstraction levels within a single `hls` dialect (`mlir::scalehls::hls`):

**Functional Dataflow** (high-level, algorithm-oriented):
- `DispatchOp` — contains a graph of tasks to be dispatched in dataflow
- `TaskOp` — transparent region containing ops to execute; can be fused/split freely
- `YieldOp` — terminator returning results from dispatch/task

**Structural Dataflow** (low-level, microarchitecture-oriented):
- `ScheduleOp` — isolated region with scheduled nodes (counterpart of Dispatch)
- `NodeOp` — isolated region with explicit I/O classification: inputs (read-only), outputs (written), params (scalars)
- `BufferOp` — on-chip memory with configurable ping-pong depth
- `StreamOp` — FIFO channel with `stream_read`/`stream_write` ops

### HIDA's Compilation Pipeline (`lib/Transforms/Passes.cpp:140-298`)
The `hida-pytorch-pipeline` proceeds in 14 stages:

1. **TOSA/Linalg optimization** — elementwise fusion, dataflow creation from linalg patterns
2. **Bufferization** — tensor IR → memref IR
3. **Linalg to Affine** — linalg generics → affine loop nests
4. **Affine loop fusion** — fuse producer-consumer loops
5. **Buffer placement** — classify buffers as BRAM/DRAM based on size threshold
6. **Loop tiling** — tile loops with configurable tile size
7. **Local buffer allocation** — create tile-sized local buffers
8. **Affine loop dataflowing** — create DispatchOp/TaskOp hierarchy from affine loops
9. **Lower dataflow** — Functional (Task/Dispatch) → Structural (Node/Schedule/Buffer)
10. **Eliminate multi-producer/consumer** — fix shared buffer violations
11. **Parallelize dataflow nodes** — intensity-aware + connection-aware loop unrolling
12. **Memory optimization** — reduce II, vectorize buffers
13. **Convert dataflow to func** — nodes become sub-functions
14. **Directive generation** — emit HLS pragmas, create AXI interfaces

### Key HIDA Design Decisions
- **Inter-task communication is memory-mapped**: Tasks communicate through `BufferOp` (memref), not streams. Only scalar values use `StreamOp`.
- **No tensor-level stream encoding**: The `StreamType` is `hls.stream<elementType, depth>` — a simple FIFO with no layout/access-pattern metadata.
- **Single-level tiling**: All kernels tiled uniformly with `--loop-tile-size`.
- **Flat DSE**: Intensity+Connection-aware parallelization, but no multi-level design space hierarchy.

## Part 2: How StreamTensor Improves on HIDA

StreamTensor is the next-generation compiler from the same group, published at MICRO '25. It fundamentally changes how inter-kernel data communication works — from memory-mapped buffers to streaming FIFOs with rich type-level metadata.

### Key Improvement 1: Iterative Tensor (itensor) Type System
HIDA uses standard `memref` between nodes. StreamTensor introduces `itensor` that encodes:
- **Element shape**: the tensor slice (tile) shape per iteration
- **Iteration space**: `[tripcount_0, ...] * [step_0, ...]` defining how tiles are produced/consumed
- **Iteration map**: affine map from iteration dimensions to data dimensions

This enables the compiler to verify stream layout compatibility at the type level. When a producer's output `itensor` matches a consumer's input `itensor`, they can be connected via a simple FIFO. When they differ, a stream layout converter is automatically inserted.

### Key Improvement 2: Stream-Based Kernel Fusion
HIDA fuses tasks at the Linalg level (pattern matching). StreamTensor fuses at the dataflow kernel level using the `itensor` type:
- **Algorithm 1** computes the minimal ping-pong buffer for layout conversion between incompatible `itensor` types
- **Algorithm 2** greedily fuses kernels in topological order, constrained by on-chip memory budget `Cmax`
- Any two kernels can be fused by design (the converter handles layout mismatches)

### Key Improvement 3: Automatic DMA Generation
In HIDA, external memory interfaces are handled manually or through buffer placement heuristics. StreamTensor's `kernel` operation has tensor I/O at its boundary — conversions from tensor to `itensor` at the kernel boundary automatically become DMAs with:
- Ping-pong buffering to hide memory latency
- Pack/widen transformations for bandwidth optimization
- Vectorized data access patterns

### Key Improvement 4: LP-Based FIFO Sizing
HIDA uses fixed-depth buffers. StreamTensor models token production/consumption as piecewise linear functions, then solves an LP to minimize total FIFO area while preventing deadlock. This requires profiling pipeline II and initial delay from the vendor HLS tool mid-compilation.

### Key Improvement 5: Hierarchical Design Space Exploration
HIDA has flat intensity+connection-aware parallelization. StreamTensor explores three nested design spaces:
1. **Linalg Tiling Space** (tile sizes, unroll factors, vectorization, permutation) — searched via Optuna
2. **Kernel Fusion Space** (which kernels to fuse) — Algorithm 2 with feedback from tiling
3. **Resource Allocation Space** (FIFO sizes, memory placement, graph partition) — LP/ILP

### Key Improvement 6: LLM Support
HIDA targets CNNs (ResNet, MobileNet, VGG). StreamTensor targets LLMs (GPT-2, Qwen, Llama, Gemma) — fusing entire transformer blocks onto a single FPGA with all intermediate results streaming on-chip.

### Summary of IR Differences

| Concept | HIDA | StreamTensor |
|---------|------|--------------|
| Top-level structure | `DispatchOp` → `TaskOp` | `KernelOp` → `TaskOp` |
| Structural level | `ScheduleOp` → `NodeOp` → `BufferOp` | Same (lowered from kernel) |
| Tensor communication | `memref` through `BufferOp` | `itensor` through FIFOs |
| Stream type | `hls.stream<T, depth>` (scalar) | `itensor<shape, iterspace, itermap>` (tensor tiles) |
| Layout conversion | N/A | `itensor_converter` with ping-pong buffer |
| DMA | Implicit via buffer placement | Explicit via kernel boundary conversion |
| FIFO sizing | Fixed depth | LP-optimized |

#### Step 1.1: Define ITensorType
**File**: `include/scalehls/Dialect/HLS/HLSTypes.td` (add after line 25)

Add a new type `ITensorType` with parameters:

**Implementation**: `lib/Dialect/HLS/HLS.cpp` — add custom parser/printer for the type (the `AffineMap` parameter needs special assembly format handling since `assemblyFormat` can't handle it automatically).

**Verification logic**: Ensure `iterTripCounts.size() == iterStepSizes.size()`, ensure `iterationMap.getNumInputs() == iterTripCounts.size()`, ensure `iterationMap.getNumResults() == elementShape.size()`.

### Phase 2: ITensor and Structure Operations
**Depends on**: Phase 1

#### Step 2.1: Structure Operations (Table 3 of paper)
**File**: `include/scalehls/Dialect/HLS/HLSOps.td`

Add these operations (coexisting with existing Dispatch/Task):

**`KernelOp`** — Top-level dataflow kernel (like Figure 1 in paper)
- Trait: `IsolatedFromAbove` (like NodeOp, not transparent like TaskOp)
- Arguments: `Variadic<TensorType>` sources
- Results: `Variadic<TensorType>` results  
- Region: contains `STTaskOp` operations communicating via `itensor` values
- At the kernel boundary, tensor arguments are conceptually converted to/from `itensor` — these become implicit DMAs during materialization
- Body block arguments have `ITensorType` (even though op arguments have `TensorType`)

**`STTaskOp`** (StreamTensor Task) — Dataflow task within kernel
- Trait: `SingleBlockImplicitTerminator<"STYieldOp">`, transparent (not isolated)
- Uses destination-carried semantics for itensor: `inits` operands receive itensor destinations, `results` are updated itensors
- Has `@name` attribute for identifying the task

**`STYieldOp`** — Terminator for KernelOp and STTaskOp

**Design decision**: Keep existing `DispatchOp/TaskOp/NodeOp/ScheduleOp` for backward compatibility. The new `KernelOp/STTaskOp` are used by the StreamTensor pipeline. Eventually `KernelOp` lowers through the existing structural ops.

#### Step 2.2: ITensor Operations (Table 1 of paper)
**File**: `include/scalehls/Dialect/HLS/HLSOps.td`

All new ops with `ITensorType` operands/results:

| Operation | Key Details |
|-----------|-------------|
| `ITensorEmptyOp` | No operands, returns `ITensorType`. Placeholder (no FIFO backing). |
| `ITensorInstanceOp` | No operands, returns `ITensorType`. Creates a concrete FIFO. |
| `ITensorReadOp` | Operands: `source: ITensorType`, `init: TensorType`. Returns tensor value. Pulls one tile from FIFO. |
| `ITensorWriteOp` | Operands: `value: TensorType/AnyType`, `dest: ITensorType`. Returns updated `ITensorType`. Destination-carried push. |
| `ITensorCastOp` | Source → result `ITensorType` cast (no layout change). |
| `ITensorReassociateOp` | Reassociate element shape/iteration space dimensions. From tensor expand/collapse_shape. |
| `ITensorConverterOp` | Source → result layout conversion. Has ping-pong buffer size attribute (computed by Algorithm 1). |
| `ITensorChunkOp` | Split one itensor into variadic results along a dimension. |
| `ITensorConcatOp` | Join variadic itensors into one result. |
| `ITensorForkOp` | Broadcast one itensor to multiple identical consumers. |
| `ITensorJoinOp` | Round-robin join from multiple producers. |

**Critical implementation detail for `ITensorWriteOp`**: It uses destination-carried semantics (like `scf.for` iter_args). The `dest` itensor is passed in, the write appends to it, and the `result` is the updated itensor. This enables SSA-based tracking of FIFO state.

#### Step 2.3: Stream-Level Operations (Table 2 of paper)
**File**: `include/scalehls/Dialect/HLS/HLSOps.td`

The existing `StreamOp`, `StreamReadOp`, `StreamWriteOp` can be reused. Add:
- `ITensorToStreamOp` — conversion bridge (must be eliminated during bufferization)
- `StreamToITensorOp` — reverse bridge
- `StreamBufferOp` — ping-pong (double) buffer, distinct from `BufferOp`
- `StreamCastOp` — stream type cast without layout change

#### Step 2.4: Update Visitor and Interfaces
**File**: `include/scalehls/Dialect/HLS/Visitor.h` — add HANDLE macros for all new ops
**File**: `include/scalehls/Dialect/HLS/HLSInterfaces.td` — add `ITensorOpInterface` for common itensor op queries

**Potential obstacle**: The destination-carried semantics of `ITensorWriteOp` interact with MLIR's `scf.for` iter_args. The verifier must ensure that itensor values flow correctly through loop-carried dependencies. Study how upstream MLIR's `tensor.insert_slice` handles this pattern.

### Phase 3: Linalg-to-Kernel Conversion Passes
**Depends on**: Phase 2

These passes implement the left side of Figure 4 (Linalg stage → Linalg Tiling → Linalg to Dataflow).

#### Step 3.1: `ConvertLinalgToKernelPass`
**File to create**: `lib/Transforms/Dataflow/ConvertLinalgToKernel.cpp`

This replaces `CreateDataflowFromLinalg.cpp` for the StreamTensor flow.

**Algorithm** (matching paper Section 4.1, Figure 6(a)→(c)):
1. For each tiled linalg operation (wrapped in `scf.for` with `extract_slice`/`insert_slice`):
   - Analyze the surrounding `scf.for` loops to extract iteration tripcounts and step sizes
   - Analyze `extract_slice`/`insert_slice` offsets and sizes to determine the `iterationMap` and `elementShape`
   - Create a `KernelOp` with tensor arguments
   - Convert kernel body block arguments from `TensorType` to `ITensorType` using the inferred type
   - Replace `extract_slice` with `ITensorReadOp`
   - Replace `insert_slice` with `ITensorWriteOp`
   - Wrap the tiled computation loop nest in an `STTaskOp`

**Key function signatures**:
```cpp
ITensorType inferITensorType(AffineLoopBand &loops, tensor::ExtractSliceOp extract);
void convertTiledLinalgToKernel(scf::ForOp outerLoop, linalg::GenericOp generic);
```

**Potential obstacle**: The tiled linalg may have complex extract_slice patterns (dynamic offsets, non-unit strides). Start by supporting the common case (static offsets proportional to loop induction variables) and add dynamic support later.

#### Step 3.2: `ConvertTensorToKernelPass`
**File to create**: `lib/Transforms/Dataflow/ConvertTensorToKernel.cpp`

Handles non-linalg tensor operations (pad, collapse_shape, expand_shape, chunk, concat) that appear between kernels. These become simple pass-through kernels.

#### Step 3.3: `PackKernelInterfacePass`
**File to create**: `lib/Transforms/Dataflow/PackKernelInterface.cpp`

**Algorithm** (paper Section 4.2, Figure 6(d)):
1. For each kernel, examine input/output tensor types
2. Insert `tensor.pack` before kernel to convert default layout → tiled layout (e.g., `tensor<64x64>` → `tensor<4x4x16x16>`)
3. Insert `tensor.unpack` after kernel to convert back
4. For static tensors (weights), fold pack into the tensor data (no runtime cost)
5. For dynamic tensors (activations), attempt to fold pack/unpack with neighboring kernels

#### Step 3.4: `WidenKernelInterfacePass`
**File to create**: `lib/Transforms/Dataflow/WidenKernelInterface.cpp`

Widens tensor elements to vectors for maximum memory bandwidth:
- With 512-bit DDR/HBM and uint8 elements, group 64 elements into `vector<64>`
- The packed `tensor<4x4x16x16>` becomes `tensor<4x4x2x2xvector<8x8>>`
- Updates `ITensorType` element shapes accordingly

#### Step 3.5: `MaterializeKernelPass`
**File to create**: `lib/Transforms/Dataflow/MaterializeKernel.cpp`

**Algorithm** (paper Section 4.3.1, Figure 7(a)→(b)):
1. For each kernel, materialize the implicit DMA at boundaries:
   - Input boundary: generate `scf.for` loop that loads from packed tensor, stores to ping-pong buffer, pushes to FIFO via `ITensorWriteOp`
   - Output boundary: generate loop that pulls from FIFO, stores to ping-pong buffer, writes to external memory
2. These DMA tasks are wrapped in `STTaskOp` operations within the kernel
3. After materialization, the kernel contains: DMA-in tasks → compute tasks → DMA-out tasks

**Potential obstacle**: The DMA materialization must correctly handle the packed+widened tensor layout. The loop nest structure (indices, bounds, strides) must match the `ITensorType` iteration space exactly.

**Files to modify**:
- `include/scalehls/Transforms/Passes.td` — add pass definitions with options
- `include/scalehls/Transforms/Passes.h` — add `createXxxPass()` factory functions
- `lib/Transforms/CMakeLists.txt` — add new .cpp files to build

### Phase 4: ITensor Optimization and Kernel Fusion
**Depends on**: Phase 3

#### Step 4.1: `FoldITensorPass`
**File to create**: `lib/Transforms/Dataflow/FoldITensor.cpp`

**Algorithm** (paper Section 4.3.2, Figure 7(b)→(c)):
- When an `ITensorWriteOp` in one task connects to an `ITensorReadOp` in the next task via a FIFO, and both have exactly matching memory access patterns:
  - Eliminate the FIFO and merge the two local buffers
  - The fetched tile is passed directly to the compute op
- This is more restrictive than stream-based fusion (requires exact pattern match) but saves memory and latency

**Key check**: Access pattern match — compare the affine access maps of the write's source and the read's destination. If identical, folding is safe.

#### Step 4.2: `VectorizeITensorPass`
**File to create**: `lib/Transforms/Dataflow/VectorizeITensor.cpp`

**Algorithm** (paper Section 4.3.3, Figure 7(c)→(d)):
1. For each itensor FIFO between tasks, determine the required bandwidth based on kernel parallelism
2. Vectorize the itensor: change element shape from `tensor<16x16>` to `vector<2x4>`
3. On the write side: generate `vector.transfer_read` from buffer → `ITensorWriteOp` to FIFO
4. On the read side: generate `ITensorReadOp` from FIFO → `vector.transfer_write` to buffer
5. Update the `ITensorType` to reflect the vectorized element

#### Step 4.3: `EnsureITensorSingleUsePass`
**File to create**: `lib/Transforms/Dataflow/EnsureITensorSingleUse.cpp`

For each itensor value with multiple consumers, insert `ITensorForkOp` to create duplicated streams. This is the streaming equivalent of HIDA's `EliminateMultiConsumer`.

#### Step 4.4: `ConvertEmptyToInstancePass`
**File to create**: `lib/Transforms/Dataflow/ConvertEmptyToInstance.cpp`

Convert all `ITensorEmptyOp` (placeholder) to `ITensorInstanceOp` (concrete FIFO) after the itensor graph is finalized. Sets initial FIFO depths (will be optimized by LP later).

#### Step 4.5: `SimplifyTaskStructurePass`
**File to create**: `lib/Transforms/Dataflow/SimplifyTaskStructure.cpp`

Clean up the task hierarchy: merge adjacent tasks with compatible iteration spaces, remove empty tasks, inline single-op tasks.

#### Step 4.6: `StrategyMergeTaskPass` (Kernel Fusion)
**File to create**: `lib/Transforms/Dataflow/StrategyMergeTask.cpp`
**File to create**: `lib/Transforms/Dataflow/ITensorConverterUtils.cpp` (utility)

This is the most algorithmic pass — implements kernel fusion (Algorithms 1 and 2 from the paper).

**Algorithm 1 — Converter Generation** (`ITensorConverterUtils.cpp`):
```
Input: src ITensorType, res ITensorType
Output: bufShape (ping-pong buffer shape), beforeLoop (shared loop index)

1. Initialize bufShape=[], beforeLoop=0, sharedLoops=[]
2. For each data dimension dim:
   a. If src.elementSize(dim) != res.elementSize(dim): break
   b. Get srcExpr = src.iterMap[dim], resExpr = res.iterMap[dim]  
   c. If both are dimension expressions at same position:
      - Append src.elementSize(dim) to bufShape
      - Record as shared loop, increment beforeLoop
   d. Else: break
3. Filter out shared loops whose parent loops are not shareable
4. Append remaining full data shape to bufShape
5. Return {bufShape, beforeLoop}
```

**Algorithm 2 — Kernel Fusion Exploration** (`StrategyMergeTask.cpp`):
```
Input: G (kernel graph), Cmax (max on-chip memory per fused kernel)
Output: F (fusion groups), C (costs)

1. F=[{∅}], C=[0], M={} // M maps node→fusion group index
2. For n in topological_sort(G):
   a. Gather fusion candidates from predecessors
   b. For each predecessor p: compute memory cost of fusing n with p's group
   c. Select nearest valid candidate f_idx with cost f_cost
   d. If no candidate or f_cost + C[f_idx] > Cmax:
      - Create new fusion group {n}
   e. Else:
      - Add n to group f_idx, update cost
3. Write fusion_index back to each kernel
```

**Pass options**: `Cmax` (max fusion cost, typically total BRAM/URAM on target FPGA).

**Potential obstacles**:
- Algorithm 1 requires comparing `AffineMap` expressions analytically. Use MLIR's `AffineExpr` comparison utilities.
- Algorithm 2 is greedy and may produce suboptimal results. The paper acknowledges this and uses Optuna feedback from the tiling space to refine.
- The `ITensorConverterOp` materialization (generating the actual ping-pong buffer implementation with scf.for loops) is complex — defer full implementation to Phase 5.

### Phase 5: Lowering and Bufferization
**Depends on**: Phase 4

#### Step 5.1: `LowerITensorToStreamPass`
**File to create**: `lib/Transforms/Dataflow/LowerITensorToStream.cpp`

This is the critical pass that converts `itensor`-level IR to `stream`-level IR (paper Section 3.1.3).

**Algorithm**:
1. For each `ITensorInstanceOp`: create `StreamOp` with `depth` from itensor analysis
2. For each `ITensorWriteOp`: generate loop nest (from itensor iteration space) containing `StreamWriteOp`
3. For each `ITensorReadOp`: generate loop nest containing `StreamReadOp`
4. For each `ITensorConverterOp`: generate two loop nests connected by a ping-pong `StreamBufferOp`
5. For each `ITensorForkOp`: generate duplicating logic (read once, write to multiple streams)
6. Strip `ITensorType` information (stream layout metadata not needed after this point)

After this pass, only `StreamOp`/`StreamReadOp`/`StreamWriteOp` and `StreamBufferOp` remain.

**Key constraint**: The `STTaskOp` at itensor level uses destination-carried semantics. After lowering to stream level, tasks use mutable stream semantics (the same `%stream` is read/written without SSA chaining). This matches the paper's description in Section 3.2.2.

#### Step 5.2: Extend `BufferizeDataflowPass`
**File to modify**: `lib/Transforms/Dataflow/BufferizeDataflow.cpp`

Add patterns for:
- `KernelOp` results → buffer allocation
- `STTaskOp` results → buffer allocation
- `StreamBufferOp` → `memref.alloc` with ping-pong semantics

#### Step 5.3: `ReduceStreamDepthPass`
**File to create**: `lib/Transforms/Dataflow/ReduceStreamDepth.cpp`

Applies LP FIFO sizing results (from Phase 6) to set optimal stream depths on all `StreamOp` declarations. If LP results aren't available, uses a conservative heuristic.

#### Step 5.4: `GenerateDirectivePass`

Generates HLS pragma attributes:

- `#pragma HLS STREAM variable=X depth=D` for each FIFO

#### Step 5.5: `MaterializeDirectivePass`
**File to create**: `lib/Transforms/Directive/MaterializeDirective.cpp`

Converts directive attributes to IR annotations that the emitter can translate to pragmas.

#### Step 5.6: Adapt `ConvertDataflowToFuncPass`
**File to modify**: `lib/Transforms/Dataflow/ConvertDataflowToFunc.cpp`

Extend to handle `KernelOp`:
- Each kernel becomes a top-level function with `#pragma HLS DATAFLOW`
- Each `STTaskOp` within becomes a sub-function
- Stream arguments are passed by reference (not value)

### Phase 6: Design Space Exploration

#### Step 6.1: Optuna Integration
**File to create**: `lib/Bindings/Python/StreamTensorDSE.py`
**File to create**: `lib/Transforms/DSE/OptunaInterface.cpp`

Architecture:
- Python script drives the search loop using Optuna's TPE (Tree-structured Parzen Estimator) sampler

- Hyperparameters: `default_tile_size`, `overall_unroll_size`, `Cmax`

The C++ side exposes:
```cpp
// Evaluate a design point. Returns {latency_estimate, resource_estimate}
std::pair<double, double> evaluateDesignPoint(
    ModuleOp module, const TilingConfig &config, const FusionConfig &fusion);
```

#### Step 6.2: LP FIFO Sizing
**File to create**: `lib/Transforms/DSE/LPFIFOSizing.cpp`
**File to create**: `lib/Transforms/DSE/LPFIFOSizing.h`

**Algorithm** (paper Section 5.3):

1. **Token Behavior Model**: For each kernel, model token production as piecewise linear function using (pipeline_II, initial_delay, total_latency)

2. **Maximum Token Calculation**:
   - If source throughput > target: `max_tokens = min(T, T - floor((L - delay) / II_target))`
   - If source throughput < target: `max_tokens = min(T, ceil((delay - D) / II_source))`

3. **LP Formulation**:
   - Variables: `delay[i][j]` for each edge (i,j) in kernel graph
   - Objective: minimize `sum(delay[i][j])` over all edges
   - Constraints: for all kernel pairs (u,v) and all paths between them: `sum(delay[i][j] on path) >= threshold(u,v)` where `threshold(u,v) = max accumulated initial delays over all paths`
   - Convert `delay` values to `max_tokens` values, set as FIFO depths

4. **Equalization Strategy**: 
   - Normal: use original pipeline IIs
   - Conservative: scale all IIs to match slowest kernel (smaller FIFOs, possible latency increase)

**LP solver**: Use GLPK (GNU Linear Programming Kit). Add as optional CMake dependency. If not available, fall back to heuristic: set all FIFO depths to `max(2, total_tokens / num_kernels)`.

#### Step 6.3: Vendor HLS Profiling
**File to create**: `lib/Transforms/DSE/VendorHLSProfile.cpp`

Mid-flow profiling to get pipeline II and initial delay:
1. After `ConvertDataflowToFunc`, emit temporary HLS C++ for each kernel function
2. Invoke `vitis_hls` in synthesis-only mode (`-flow syn`)
3. Parse the XML synthesis report for timing metrics
4. Attach `KernelTimingAttr` to each kernel
5. Cache results to avoid re-profiling during DSE iterations

Use `llvm::sys::ExecuteAndWait` for process invocation. Run multiple kernel syntheses in parallel using `std::async`.

**Potential obstacle**: Vitis HLS synthesis takes minutes per kernel. For DSE with many iterations, this becomes the bottleneck. Mitigations:
- Cache profiling results keyed by kernel hash (same kernel = same metrics)
- Run kernel syntheses in parallel
- Use analytical estimates for early DSE iterations, profile only the final candidate

#### Step 6.4: ILP Graph Partitioning
**File to create**: `lib/Transforms/DSE/ILPGraphPartition.cpp`

For multi-die FPGAs (e.g., multi-SLR U55C):
- Variables: binary assignment of each task to a die
- Objective: minimize inter-die communication + resource imbalance
- Constraint: one-hot assignment per task

Use GLPK's integer programming mode. This is only needed for designs spanning multiple dies.

## Potential Obstacles and Mitigations

### Obstacle 1: ITensorType Complexity
The `ITensorType` with `AffineMap` parameter is unprecedented in HIDA. MLIR's type infrastructure handles it, but the parser/printer/hasher must be carefully implemented.

**Mitigation**: Start with a simplified `ITensorType` that uses identity maps, then add full affine map support.

### Obstacle 2: Destination-Carried Semantics for ITensor
The SSA-based destination-carried pattern (`%result = itensor_write %value into %dest`) requires careful handling in MLIR's dominance and use-def analysis.

**Mitigation**: Study how `tensor.insert_slice` and `scf.for` iter_args handle this pattern in upstream MLIR. Copy the same approach.

### Obstacle 3: Vendor Tool Integration
The LP FIFO sizing requires profiling pipeline II from Vitis HLS mid-compilation. This creates an external dependency and significant compilation time.

**Mitigation**: 
- Make profiling optional (use heuristic estimates by default)
- Cache profiling results aggressively
- Run profiling in parallel across kernels
- Support a `--profiling-results=file.json` flag to preload results

### Obstacle 4: LLM Model Size
LLM models have many layers. Compiling an entire model may hit MLIR memory/time limits.

**Mitigation**: 
- Compile one transformer block at a time (the block is reused across layers)
- Use the runtime to sequence block execution with different weights
- This matches the paper's approach (Section 6.1: "triggered multiple times with different weight parameters")

### Obstacle 5: MLIR Version Compatibility
HIDA is built on a specific MLIR version. Some upstream passes may have changed APIs.

**Mitigation**: 
- Pin to a known-good LLVM/MLIR commit
- Abstract over API differences in utility functions
- Test compilation early in Phase 1
